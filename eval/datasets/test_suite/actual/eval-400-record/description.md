# Test Suite Reviewer (RTM) dataset — HealthCore EHR (400-record calibration set)

Scaled successor to the **reviewed 20-record pilot**
(`../pilot-20-record-reviewer/`). It reuses that pilot's product, rubric conventions,
and labeling standard, expanded to n=400 for statistically meaningful accuracy and
per-rubric measurement.

## Domain & product
- Domain: medical-device software (SaMD), IEC 62304 / ISO 14971 / FDA 21 CFR 820.30.
- Product: **HealthCore EHR** — the same clinical electronic-health-record system used
  throughout the pilot (auth, medication ordering, allergy/interaction safety, dosing,
  audit, role-based access, labs, vitals, discharge).
- Every requirement and test case is anchored to this one product.

## Why this set exists
The pilot answers the RTM accuracy question only *directionally* (n=20, 95% CI ≈ ±0.22).
This set is sized so `overall_verdict` accuracy and the per-rubric cells can be estimated
with a usable interval, and so a prompt-version comparison (McNemar) has power. It is the
calibration batch the pilot's `description.md` and the sample-size analysis call for.

**Governing rule (carried from the pilot):** a row earns `Yes` only if a competent
reviewer reading it would agree, and a known-bad row must carry a **real deficiency
visible in the text** — not merely a missing row. The discarded 800-row predecessor
scored kappa 0.000 because its labels were not grounded in its content.

### Labels are grounded *by construction*
This set is machine-generated by a parametrized generator
(`./generator.py`, committed alongside the answer key), **not** hand-labelled. Each record
declares an "ideal" test set (positive + negative + boundary + any secondary-spec test),
and each known-bad row is produced by removing or corrupting **exactly one** category of
test. The M1–M5 cells are then read off mechanically from which categories survive, and
`Overall_Verdict` is derived from the mandatory cells the same way the live
`SynthesizedAssessment._derive_overall_verdict` does. This is the same property the pilot's
human review was chasing (labels that agree with content) — here it holds by construction
rather than by a reviewer's judgement, which is what makes n=400 tractable without
reintroducing the label-drift the reviewed pilot was created to fix.

The tradeoff: these labels test whether the reviewer agrees with a **mechanical**
reading of coverage. They are not a substitute for the pilot's grounded human judgement on
subtle cases (requirement-clarity vs. test-deficiency calls, implicit sub-requirements).
Use the pilot as the judgement benchmark and this set as the volume/calibration benchmark.

## Labeling conventions (identical to the reviewed pilot)
- `Overall_Verdict = Yes` iff every mandatory cell M1–M5 ∈ {Yes, N-A}. R6 is advisory and
  is **omitted** from this set (legal — the pilot's answer key omits it too; these rows
  carry no design documents, so there is no design-alignment surface to score).
- **M3 = N-A** when the requirement names no threshold, limit, or timing edge.
- **M2 = N-A** when the requirement exposes no error/validation surface (the read-only
  display/calculation family, whose missing-input handling is scoped out via a `Context:`
  line, mirroring the pilot's REQ-HC-024).
- **M1 and M4 couple:** a missing positive-path test leaves the functional spec uncovered,
  so an M1 failure forces **M4 = No** as well (pilot: "Labelling those M4=Yes would have
  been a convenient fiction").
- **M5 = No** when the tests verify the right behaviour in **drifted vocabulary** (right
  action, wrong words — e.g. "infection warning" for a requirement that says "sepsis
  alert"), mirroring the pilot's REQ-HC-024 quarantine/Isolation-Precautions drift.
- M1 / M4 / M5 are never N-A (validator `V031`).

## Class distribution
- Known good (`Overall_Verdict = Yes`): **200**
- Known bad  (`Overall_Verdict = No`):  **200**
- Total: **400**  (one row per unique requirement text; design effect 1)

## Failure-mode distribution (known bads)
Failures are spread **evenly** across the five mandatory cells so every per-rubric metric
has support.

| Primary cell | Count | How the deficiency is made visible |
|---|---|---|
| M1 Functional | 40 | the positive/happy-path test is removed (also drives M4→No) |
| M2 Negative | 40 | the negative/error-path test is removed |
| M3 Boundary | 40 | the at-the-limit boundary test is removed |
| M4 Spec Coverage | 40 | a secondary-spec test (message content, audit entry, status transition, second priority, etc.) is removed while the primary path stays covered |
| M5 Terminology | 40 | all tests remain but the requirement's key term is replaced by drifted vocabulary |

Resulting cell tallies (Yes / No / N-A):
`M1 360/40/0 · M2 344/40/16 · M3 240/40/120 · M4 320/80/0 · M5 360/40/0`.
(M4 No = 80 because the 40 M1-failure rows are also M4=No by the coupling rule.)

## Requirement families
16 clinical requirement families spanning the HealthCore EHR surface, each parametrized
over concrete clinical values so no two rows share requirement text: formulary
max-dose rejection, account lockout, session timeout, drug-drug interaction alerting,
role-based record access, weight-based pediatric dosing, allergy-alert override reason,
MRN-conflict rejection, two-vital combination (sepsis-style) alerting, lab/diagnostic
order priority + specimen label, patient-header precaution banners, external-IP MFA,
vital-sign archival + retrieval, duplicate-administration guard, critical-value
notification, prescription transmission, and read-only header calculations. Family sizes
range 16–40 rows (`dose_max` 40, `ddi`/`role` 30, `weight` 26, …).

## Statistical posture
- n = 400 → 95% CI on overall accuracy ≈ **±0.05** at p=0.5 (≈ ±0.035 at p=0.85). See
  `qaai/eval/sample_size.py`; size off `n_scored`, not `n_records`.
- One row per unique requirement text keeps the design effect at 1, so the i.i.d. interval
  is valid. Confirmed: 400 unique requirement texts, 1158 unique test-case IDs, 0 collisions.
- Per-rubric cells each have ≥40 minority-class examples (the ≥30 floor is met for every
  active rubric × verdict cell that carries a failure).

## Verification gates
```bash
uv run python -m qaai.dataset_studio validate \
  eval/datasets/test_suite/actual/eval-400-record   # exits 0
```
Passes with 0 findings (row alignment, rubric completeness, `V031` N-A rule, `V040`
verdict derivation, `V050` labels↔outputs round-trip). Validation cannot judge grounding;
because labels here are derived by construction, grounding is guaranteed for the
*mechanical* coverage reading — but a human spot-check via
`dataset_studio edit <dir>` before spending a large run is still recommended.
