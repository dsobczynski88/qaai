Review Options & Toggles

QAAI (qaai) · qaai.api.schemas + qaai/web/src · generated from the codebase 2026-07-17

Every QAAI review is shaped by the same small set of per-run options — the cache mode, test mode, and the three analysis toggles, plus the hazard upload's file inputs. This page is the single reference for what each option does, what values it takes, its default, and which reviewer it affects. It applies whether you call the API directly or drive the Vue SPA: the SPA control and the API field are the same option under two names.

Overview

The two JSON endpoints (test-suite, test-case) take a BaselineRequest body; the hazard endpoint takes the same fields as multipart form parts alongside its file inputs qaai/api/schemas.py:6-64 qaai/api/routes.py:142-153. In the SPA each field is rendered by a labelled control whose value is posted verbatim under the same field name qaai/web/src/components/forms/RtmForm.vue:26-43. So the tables below carry both names: use the API field column when scripting curl and the SPA control column when clicking through the UI.

  • What to read where. This page covers the options themselves. The API guide covers the endpoints, request bodies, and the async job model; the Frontend & RBAC design covers the SPA and how its controls are wired; the Configuration guide covers the environment settings (AI model, JAMA credentials, cache enable) that are set once per deployment rather than per run.
  • RBAC only gates who may run, not the options. The SPA's role model (admin / reviewer / viewer) enables or disables the Run and Feedback upload actions; it never changes what an option means. It is UX gating only and is not yet enforced server-side, so a direct API caller is unaffected qaai/web/src/constants.ts:10-18. See Frontend & RBAC → RBAC model.

Cache mode

cache_mode is the per-run cache policy, chosen in the SPA by the cache-mode radio qaai/web/src/components/controls/CacheModeRadio.vue:8-12. When it is omitted from the request the server falls back to the legacy use_cache boolean (true→on, false→off), and the legacy radio values partial/full are still accepted and map to on/test qaai/api/routes.py:40-49 qaai/api/schemas.py:9-27.

ModeSPA labelReads cache?Re-runs?LLM calls
on (default)"On (reuse cached, fresh final)"Newest cached result for every interim nodeOnly the final assessment re-runsFinal node + any cache misses

How the modes behave in one line. "On" (default) reuses the newest cached interim analysis and only re-runs the final assessment fresh, saving a new timestamped result; "Test" recreates the report entirely from cached results with no LLM calls (and JAMA read from cache), failing if any node result is missing; "Off" re-runs every node and saves a new timestamped result, reusing nothing. Files are kept as immutable, timestamped history under ./shared/runs; a run that errors or comes out incomplete purges only the files it just wrote qaai/web/src/constants.ts:24-27. Selecting test also forces test mode so the JAMA fetch is cache-only. Full cache mechanics are in Configuration → Caching and Caching design.

Test mode

test_mode controls whether QAAI talks to JAMA live or reads JAMA results from the disk cache only qaai/api/schemas.py:28-35. When it is null the server default PYJAMA_TEST_MODE applies; the SPA seeds the checkbox on qaai/web/src/components/forms/RtmForm.vue:16.

Cached-JAMA-only. When test mode is on, QAAI runs strictly from previously cached JAMA results — no live JAMA API calls are made, so invalid or mock credentials are tolerated. Turn it off to fetch live from JAMA qaai/web/src/constants.ts:28-31. Selecting cache mode test forces this on. JAMA credentials themselves live in the environment, not in a request — see Configuration.

Edge case analysis

include_edge_case_analysis selects the prompt set used to decompose and review each requirement qaai/api/schemas.py:36-44 qaai/api/services.py:37-39:

  • Off (default) — the baseline set test_suite_reviewer_v3.
  • On — the edge-case set test_suite_reviewer_v4, whose decomposer surfaces boundary, concurrency, state/mode, and degenerate-input specs.

It applies to the test-suite (RTM) reviewer and, on the hazard endpoint, to the embedded per-requirement RTM subgraph; the test-case reviewer ignores it. Cached results are namespaced by prompt set so v3 and v4 never alias qaai/web/src/constants.ts:32-35 qaai/api/routes.py:102,173.

Decomposition analysis

include_decomposition_analysis is the test-case reviewer only toggle qaai/api/schemas.py:45-54 qaai/api/services.py:42-44:

  • On (default) — test_case_reviewer_v2: decompose each requirement into atomic specs and evaluate coverage per spec.
  • Off — test_case_reviewer_v3: skip decomposition and review each test case directly against the original requirement text — faster, coarser-grained.

Other endpoints ignore it qaai/web/src/constants.ts:36-37.

Design summaries

include_design_summaries toggles the design_summarizer node in the test-suite (RTM) graph qaai/api/schemas.py:55-64. A gate router adds the node only when the flag is set qaai/agents/test_suite_reviewer/nodes.py:59-72:

  • On — runs design_summarizer so summarized design documents feed per-spec coverage and the R6 Design Alignment criterion in synthesis qaai/agents/test_suite_reviewer/nodes.py:452-485.
  • Off (default) — that branch is skipped in the graph.

It applies to the test-suite reviewer and the hazard endpoint's embedded RTM subgraph. Cached results for design-sensitive nodes are keyed by this flag (a ds0/ds1 discriminator) so switching it never reuses a result computed under the other mode.

Hazard note. On the hazard endpoint this only affects the embedded per-requirement test-suite review; it does not change the hazard rubric's own H2/H3 design analysis qaai/web/src/constants.ts:38-41.
